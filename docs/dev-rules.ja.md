# 開発ルール（DF-HACK26）

## 1. 作業を始める前に宣言する

- 誰かと作業がかぶりそうなときや、誰がやっているかをはっきりさせたいときは、GitHub の issue を立てて自分を Assignees に入れる。立てるかは各自が判断し、微調整などの小さい作業には立てなくてよい
- issue を立てたら、Discord に「#12 やります」のように一言書く
- 他の人が担当している issue のファイルを触るときは、先にその人に連絡する
- コンフリクトしたら、**すでに main に入っているほうに合わせて**、自分のブランチで直す

## 2. ブランチと PR

- main に直接 push しない。必ずブランチを切って PR を出す
- ブランチ名は `種類/issue番号-内容`。
  - 例: `feat/12-login-page`、`fix/15-api-error`、`docs/3-dev-rules`
- 1つの PR には1つの作業だけ入れる
- PR の説明は `.github/pull_request_template.md` のテンプレートどおりに書く（関連する issue・確認したこと）
- CI が通っていない PR はマージしない
- レビューは手の空いている人1人に頼む。半日たっても反応がなければ、GitHub Copilot のレビューだけでマージしてよい
- 承認されたら、PR を出した本人がマージする。main にマージすると自動でデプロイされる

## 3. コードの書き方

見た目は自動整形ツールに任せ、人が決めるのは命名とコメントだけにします。バックエンドのフレームワークが決まったら、この節を更新します。

|  | Python（バックエンド） | React / TypeScript（フロント） |
| --- | --- | --- |
| 整形 | PEP 8。`ruff format` と `ruff check` を通す | Prettier と ESLint を通す |
| ファイル名 | `snake_case.py` | コンポーネントは `PascalCase.tsx`、それ以外は `camelCase.ts` |
| 関数・変数 | `snake_case` | `camelCase` |
| クラス・コンポーネント | `PascalCase` | `PascalCase` |
| 定数 | `UPPER_SNAKE_CASE` | `UPPER_SNAKE_CASE` |

- コメントには「なぜこう書いたか」を書く。コードを読めば分かることは書かない
- コメント・issue・PR は日本語でも英語でもよい

## 4. PR を出す前とマージした後に確認すること

PR を出す前:

- [ ] 手元でアプリがエラーなく起動する
- [ ] 自分が変えた機能を、画面または API から手動で確認した
- [ ] `git diff` で、`.env` や API キーが含まれていないことを確認した

マージした後（自動デプロイが終わったら）:

- [ ] デプロイ先の URL で、デモで見せる操作を最初から最後まで手動で確認した。壊れていたら、ほかの作業より先に直す

## 5. 秘密情報と Google Cloud

- API キーなどの秘密情報はコードに書かない。リポジトリには値を空にした `.env.example` だけを置く
- 実際の値は Secret Manager に置き、メンバーはそこから取得する。Discord には貼らない
- CI/CD が使う認証情報は GitHub の Secrets に置く
- Google Cloud で新しいサービスを有効にする前に、Discord で相談する

## 6. 進捗の共有と AI ツール

- 毎日、その日の作業を終えるときに Discord に一言書く（やったこと / 次にやること / 困っていること）
